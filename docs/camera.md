# Орбитальная камера

Одна и та же камера используется во всех 3D-сценах (`html/js/camera.js`), но с разными
**ограничителями** (constraints) на сцену — это единственное, что меняется между "солнечной
системой" и "планетой".

## Модель: position + offset + матрица вращения

Как и любой другой объект сцены, у камеры есть `position` — точка-"хэндл", вокруг которой
камера орбитит (аналог `target` в классическом orbit-camera, но названа как позиция, потому
что концептуально это то же самое поле, что и `position` у сфер/кубиков — просто у камеры оно
двигает не саму камеру, а центр, вокруг которого она вращается). Дальше:

- `offset` — вектор отступа в локальном пространстве камеры, `(0, 0, radius)`: "отойти назад
  на `radius`, чтобы было что смотреть".
- `rotMat` — матрица вращения (по факту — три ортонормированных базисных вектора
  `right`/`up`/`back`, собранные в `mat4` через `Mat4FromBasis`, см. `gl.js`).
- Итоговая позиция камеры: `eye = position + rotMat * offset` (`Mat4MulDir` — умножение
  направления на матрицу, без учёта трансляции).

`theta`/`pitch`/`radius` — управляющее состояние поверх этой модели. **Углы — в градусах.**
`theta` — азимут (yaw), `pitch` — подъём **над горизонтом** (`pitch = 0` → взгляд по
горизонту, `pitch = 90` → сверху вниз). `update(dt)` каждый кадр пересчитывает из них
`right`/`up`/`back` и складывает в `rotMat`, `offset` — в `(0, 0, radius)`. Держать
`theta`/`pitch` отдельно нужно: это то, что копит input-дельты и что зажимают ограничители
(`minPitch`/`maxPitch`).

```
th = theta * DEG ; p = pitch * DEG          // DEG = PI/180, в include.js
back  = (cos(p)*cos(th), sin(p), cos(p)*sin(th))
right = normalize(cross(worldUp, back))
up    = cross(back, right)
rotMat = Mat4FromBasis(right, up, back)
offset = (0, 0, radius)
eye = position + Mat4MulDir(rotMat, offset)   // = position + back * radius
```

(Раньше `phi` мерился от вертикали и `back` шёл через `sin(phi)`/`cos(phi)`; `pitch = 90 - phi`,
формула эквивалентна с точностью до перестановки sin/cos.)

View-матрица строится обычным `lookAt(eye, position, worldUp)`. Projection — обычная
перспектива (`fov`, `aspect`, `near`, `far`). `near` 0.3, `far` 10000 — большой диапазон
нужен `ship_state`/`system_travel_state`, где система рисуется в истинном масштабе (планета
~250 юнитов, дальние тела ~3600, скайбокс ~7500; см. [architecture.md](architecture.md)).
`near` держим сильно выше нуля, иначе на такой дистанции сыпется точность буфера глубины;
все сцены держат ближнюю геометрию дальше ~0.3 юнита от глаза.

Раскладка камеры на явную матрицу вращения, а не только "eye по формуле", — задел на будущее:
если камера когда-нибудь станет свободной (6DOF), `rotMat` уже есть как отдельное поле, менять
нужно будет только то, как он собирается, а не всю модель.

## Ограничители — разные на сцену

Два **позиционных** сеттера, вызываются из `OnEnter`:

```js
camera.setConstraints(minRad, maxRad, panSize, minPitch = 10, maxPitch = 80)
camera.place(pos, dist, pitch, theta = camera.theta)   // навести камеру одним вызовом
```

- `setConstraints` задаёт диапазон радиуса, полу-размер квадратной пан-зоны (`panSize`,
  мировые единицы; **`0` = камера приколочена к центру**) и диапазон `pitch`. По умолчанию
  `10..80` над горизонтом («большинство сцен»); **режим корабля — `-80..80`** (можно
  заглянуть снизу). Также **сбрасывает `autoSpeed` в 0** — сцена, которой нужен показ-спин,
  ставит его после.
- `place` — вместо четырёх строк `p=`/`setDist`/`theta=`/`pitch=`. `theta` необязателен
  (по умолчанию — текущий, для сцен, которым азимут не важен: `system`/`galaxy`).
- Азимут `theta` ни в одной сцене не ограничивается — вращение вокруг вертикали свободно.

| Сцена | `setConstraints` | `place` |
|---|---|---|
| `ship_state` | `8, 70, 12, -80, 80` | `V3(), 22, 44, 90` |
| `system_state` | `4, 22, 8` (pitch 10..80) | `V3(), 13, 41` |
| `galaxy_state` | `12, 40, 14` | `V3(), 26, 33` |
| `menu_state` | `10, 10, 0, 56, 56` (pitch пришпилен) | `V3(), 10, 56, 0` + `autoSpeed = 9` |
| транзиты | узкий радиус, `panSize 0`, широкий pitch | скриптуют pitch/theta каждый кадр |

Смена ограничителей не телепортирует камеру — `pitch`/`radius`/`position` вне новых границ
просто зажимаются (`clamp`/`clampPan`) на следующем кадре — плавный доворот, не скачок.

## Ввод: RMB-поворот, LMB-пан, колесо-зум

`input.js` не знает о камере вообще — он копит за кадр сырые данные пойнтера в **NDC**-единицах
(`pdx`/`pdy` — дельта перетаскивания, `px`/`py` — текущая позиция курсора, `wheel`,
`clicked`+`clickX`/`clickY` для короткого клика ЛКМ) плюс `btn` — какая кнопка сейчас зажата
(`0` левая, `2` правая, `-1` ничего). Контекстное меню подавлено (`contextmenu` →
`preventDefault`), чтобы ПКМ была свободна под поворот. `pdx/pdy/wheel/clicked` обнуляются в
`update()` в конце кадра; `btn/px/py` — это состояние, не событие, и переживают кадр.

Применяет всё это общий хелпер `ApplyCameraInput(ctx, dt)` в `camera.js`, который зовут
интерактивные состояния из своего `OnUpdate`:

```js
if (inp.btn === 2) ctx.camera.rot(-inp.pdx * 143, -inp.pdy * 143) // ПКМ: поворот, ~143°/ед. ≈ старые 2.5 рад
ctx.camera.zm(inp.wheel * 0.0005)                                 // колесо: шаг по zoomT (camera.zoom)
ctx.camera.upd(dt)                                                // radius = f(zoomT), clamp (camera.update)
if (inp.btn === 0) ctx.camera.panFromScreen(prevNDC, curNDC)      // ЛКМ: пан
```

Методы `rot`/`zm`/`upd` названы так руками: closure **не переименовывает** `.rotate`/`.zoom`/
`.update` (совпадают с DOM-externs), поэтому короткие имена — наши, ~12 Б экономии, см.
[optimization.md](optimization.md). Остальные методы камеры closure ужимает сам.

- **Поворот — только ПКМ.** Обе дельты идут с минусом: `-pdx` — это «нормальное» горизонтальное
  вращение (тот же знак, что был у старого px-драга), а `-pdy` **инвертирует вертикаль**
  относительно прежнего поведения (осознанно — так попросили).
- **Пан — ЛКМ.** `panFromScreen(prev, cur)` строит пик-луч для позиции курсора в прошлом и
  текущем кадре (`prev = [px - pdx, py - pdy]`), пересекает оба с плоскостью пола `y = 0`
  (`planeHit`: `t = -origin.y / dir.y`, отбрасывая почти-параллельные и уводящие назад лучи) и
  сдвигает `camera.position` на разницу попаданий — «взял мир пальцем и потащил». Результат
  зажимается `clamp(p, -panSize, panSize)` по X/Z; **`panSize = 0` = камера приколочена к
  центру** и не двигается вообще. Если один из лучей не попал в пол (смотрим на горизонт),
  пан за этот кадр просто пропускается.
- **Зум — нелинейный.** Колесо двигает `camera.zoomT` (0..1) на **фиксированный** шаг, а
  `update()` каждый кадр выводит из него дистанцию: `radius = min + (max−min)·zoomT²`.
  Квадрат → у ближней границы нотч колеса почти не двигает камеру (точная наводка на объект),
  у дальней — проматывает большой кусок. Стартовую дистанцию сцены задаёт `place(...)` (внутри
  — `setDist(r)`, обратная функция `zoomT = √((r−min)/(max−min))`); `place` вызывать **после**
  `setConstraints()`. `zoomT` переносится между сценами, но каждый `OnEnter` его перебивает.
- `camera.upd(dt)` (в коде — `upd`, «update») каждый кадр зажимает `pitch` по constraints
  (`clamp`), выводит `radius` из `zoomT` (всегда в `[min,max]`) и зовёт `clampPan()` —
  никакой «анимации отскока» не нужно, clamp сам создаёт ощущение упора. `clamp(v, lo, hi)` —
  общий хелпер в `include.js` (им же зажаты `zoomT` и пан).

Короткий клик ЛКМ (курсор почти не двигался) — это `clicked` для пикинга по сцене, отдельно от
драга; ПКМ пикингом не считается.

## Пикинг без обратной матрицы

Для клика по сфере в 3D нужен луч (origin, direction) из курсора в мировое пространство.
Стандартный путь — unproject через обратную view-projection матрицу, но это лишний код
(инверсия mat4 ~30 строк). Вместо этого луч строится прямо из базиса камеры и FOV:

```
forward = normalize(position - eye)   // = -back
right, up — те же вектора, что уже легли в rotMat при update()

ndcX, ndcY — координаты клика в [-1, 1]
halfH = tan(fov / 2)
halfW = halfH * aspect

dir = normalize(forward + right * ndcX * halfW + up * ndcY * halfH)
```

Дальше — обычное пересечение луча (`eye`, `dir`) со сферами объектов (классическая формула
через дискриминант), см. `PickObject`/`IntersectSphere` в `objects.js`. Работает только
потому, что камера всегда смотрит точно на `position` (честный orbit-look-at, без
произвольного наклона) — если камера когда-нибудь станет свободной (6DOF), этот хак придётся
заменить на unproject.

## theta, position и старт сцены

`theta` (азимут, градусы) не входит в `setConstraints` — он всегда свободный. `camera.p`
(центр орбиты) переживает смену сцены. Отсюда правило для `OnEnter`:

- **`menu` и переходы** (фиксированный ракурс, `ctx.input` не читают) передают `theta` в
  `place(...)` явно (`menu` крутит его дальше через `autoSpeed`), иначе унаследуют азимут, на
  котором игрок бросил камеру. `place` в любом случае ставит `p` (все сцены передают `V3()`),
  так что пан из прошлой сцены не переносится.
- **`system`/`galaxy`** `theta` не передают — `place(pos, dist, pitch)` оставляет текущий.

Практическое следствие для `ship_state.js`: корабль и слоты вдоль/вокруг осей X и Z, камера
входит `place(V3(), 22, 44, 90)` — взгляд сверху-сбоку (pitch 44°), ось X поперёк экрана.
Спавн врагов считает `theta * DEG` (ставит противника в `theta·DEG + PI`, «перед» кораблём со
стороны камеры), чтобы заспавненный по кнопке `Debug` враг был в кадре.

## Доворот камеры в транзит-стейтах

`hyperjump_state` и `system_travel_state` вместо «заморозки» доворачивают камеру в **3 фазы**
по своему таймеру `t`: `swingIn` (доля `k: 0→1`), `cruise` (`k = 1`), `swingBack` (`k: 1→0`),
затем `SetState(onDone())`. Каждый кадр:

```js
ctx.camera.theta = LerpAngle(theta0, targetTheta, k)   // LerpAngle в gl.js — по кратчайшей дуге, ГРАДУСЫ (wrap 360)
ctx.camera.pitch = pitch0 + (targetPitch - pitch0) * k
ctx.camera.upd(dt)                                     // upd = camera.update
```

`theta0/pitch0` (градусы) снимаются в `OnEnter`. Для **локального перелёта** `targetTheta =
atan2(-fwd.z, -fwd.x) / DEG + 9` (камера позади корабля по курсу `fwd`, чуть вбок),
`targetPitch = pitch0 + 15` (садится за дюзы), плюс `radius` едет `R_FAR → R_TUCK → R_FAR` по
тому же `k`. Сдвиг системы (`smoothstep`) — **только** в крейсере. В крейсере RMB перебивает
скрипт. Числа — под тюнинг; **эти два стейта скоро сольются в один `CreateTravelState`**, см.
[effects.md](effects.md).
