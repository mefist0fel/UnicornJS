# Орбитальная камера

Одна и та же камера используется во всех 3D-сценах (`html/js/camera.js`), но с разными
**ограничителями** (constraints) на сцену — это единственное, что меняется между "солнечной
системой" и "планетой".

## Модель: position + offset + матрица вращения

Как и любой другой объект сцены, у камеры есть `position` — точка-"хэндл", вокруг которой
камера орбитит (аналог `target` в классическом orbit-camera, но названа как позиция, потому
что концептуально это то же самое поле, что и `position` у сфер/кубиков — просто у камеры оно
двигает не саму камеру, а центр, вокруг которого она вращается). Дальше:

- `offset` — вектор отступа в локальном пространстве камеры, `(0, 0, radius)`: "отойти назад
  на `radius`, чтобы было что смотреть".
- `rotMat` — матрица вращения (по факту — три ортонормированных базисных вектора
  `right`/`up`/`back`, собранные в `mat4` через `Mat4FromBasis`, см. `gl.js`).
- Итоговая позиция камеры: `eye = position + rotMat * offset` (`Mat4MulDir` — умножение
  направления на матрицу, без учёта трансляции).

`theta`/`phi`/`radius` — управляющее состояние поверх этой модели, а не самостоятельная
система координат: `update(dt)` каждый кадр пересчитывает из них `right`/`up`/`back` (тем же
способом, что раньше строился `eye` напрямую по сферическим координатам) и складывает их в
`rotMat`, а `offset` — в `(0, 0, radius)`. Держать `theta`/`phi` отдельно всё ещё нужно: это
то, что накапливает input-дельты и то, что зажимают ограничители (`minPhi`/`maxPhi` и т.п. —
зажимать сразу матрицу вращения было бы неудобно).

```
back  = (sin(phi)*cos(theta), cos(phi), sin(phi)*sin(theta))
right = normalize(cross(worldUp, back))
up    = cross(back, right)
rotMat = Mat4FromBasis(right, up, back)
offset = (0, 0, radius)
eye = position + Mat4MulDir(rotMat, offset)   // = position + back * radius
```

View-матрица строится обычным `lookAt(eye, position, worldUp)`. Projection — обычная
перспектива (`fov`, `aspect`, `near`, `far`).

Раскладка камеры на явную матрицу вращения, а не только "eye по формуле", — задел на будущее:
если камера когда-нибудь станет свободной (6DOF), `rotMat` уже есть как отдельное поле, менять
нужно будет только то, как он собирается, а не всю модель.

## Ограничители — разные на сцену

`CreateCamera()` хранит `constraints = { minPhi, maxPhi, minRadius, maxRadius }` (азимут
`theta` не ограничивается ни в одной из сцен — вращение вокруг вертикали свободное всегда).
`camera.setConstraints(c)` вызывается из `OnEnter` состояния при входе в сцену (см.
[architecture.md](architecture.md#стейт-машина)).

- **Солнечная система** — верхняя полусфера: `minPhi = 0.15`, `maxPhi = PI/2 - 0.05`.
  Камеру нельзя увести под "плоскость эклиптики" — система всегда рассматривается сверху,
  как макет на столе. Верхняя граница чуть меньше `PI/2`, чтобы не смотреть строго в упор
  на плоскость (плоские объекты вырождаются в линию на экране).
- **Планета** — полная сфера: `minPhi = 0.05`, `maxPhi = PI - 0.05`. Планету можно облететь
  полностью, границы только у самых полюсов — избегаем `phi = 0`/`PI` (в этих точках
  `lookAt` с `worldUp = [0,1,0]` вырождается: forward-вектор совпадает с `up`).
- **Меню** — камера не управляется игроком: `theta` крутится автоматически (`theta += k*dt`
  через `autoSpeed`), `phi`/`radius` фиксированы. Ограничители похожи на солнечную систему
  (фон меню — это она же), `menu.js` просто не читает `ctx.input` в своём `OnUpdate`, поэтому
  драг/зум игрока эту сцену не трогают.

Смена ограничителей не телепортирует камеру — если текущий `phi`/`radius` выходят за новые
границы, они просто зажимаются (`clamp`) на следующем кадре, так что переход выглядит как
плавный доворот, а не скачок.

## Ввод

`input.js` не знает о камере вообще — он лишь копит за кадр сырые дельты (`dx`/`dy` от драга,
`wheel` от колеса, `clicked`+`clickX`/`clickY` для короткого клика) и обнуляет их в
`update()`, который дергает игровой цикл в конце каждого кадра. Применение — дело самой сцены
в её `OnUpdate`:

```js
ctx.camera.rotate(-ctx.input.dx * 0.005, -ctx.input.dy * 0.005)
ctx.camera.zoom(ctx.input.wheel * 0.01)
ctx.camera.update(dt)
```

`camera.update(dt)` зажимает результат по текущим constraints каждый кадр — никакой отдельной
"анимации отскока" от границы не нужно, clamp сам создаёт ощущение упора.

## Пикинг без обратной матрицы

Для клика по сфере в 3D нужен луч (origin, direction) из курсора в мировое пространство.
Стандартный путь — unproject через обратную view-projection матрицу, но это лишний код
(инверсия mat4 ~30 строк). Вместо этого луч строится прямо из базиса камеры и FOV:

```
forward = normalize(position - eye)   // = -back
right, up — те же вектора, что уже легли в rotMat при update()

ndcX, ndcY — координаты клика в [-1, 1]
halfH = tan(fov / 2)
halfW = halfH * aspect

dir = normalize(forward + right * ndcX * halfW + up * ndcY * halfH)
```

Дальше — обычное пересечение луча (`eye`, `dir`) со сферами объектов (классическая формула
через дискриминант), см. `PickObject`/`IntersectSphere` в `objects.js`. Работает только
потому, что камера всегда смотрит точно на `position` (честный orbit-look-at, без
произвольного наклона) — если камера когда-нибудь станет свободной (6DOF), этот хак придётся
заменить на unproject.
