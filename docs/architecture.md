# Архитектура и конвенции

Организация кода унаследована от предыдущего js13k-проекта (`../js13k_city`, Castle Wars JS) —
она хорошо показала себя под жёсткий бюджет размера и решётку google-closure-compiler /
внешних минификаторов. Здесь тот же подход, адаптированный под настоящий WebGL вместо
canvas2d-псевдо-3D.

## Никаких модулей, никаких классов

- Файлы — обычные `<script>`, без ES-модулей (`import`/`export` жрут байты в non-advanced
  минификации и требуют `type="module"` + CORS-нюансов при `file://`). Порядок подключения
  задаётся один раз в `html/index.html` и **является manifest'ом сборки** — `build.py` читает
  этот же порядок, чтобы не дублировать список файлов (см. [build.md](build.md)).
- Никаких `class`. Объекты создаются фабричными функциями `CreateXxx(...)`, возвращающими
  плоский объект-литерал с методами-замыканиями. Это дешевле для минификатора (нет цепочки
  прототипов, поля манглятся как обычные свойства объекта) и не требует `this`/`bind`.
- Общее изменяемое состояние — плоские глобальные переменные (`var`/`let`/`const` на верхнем
  уровне файла), а не одна большая конфигурация/синглтон-объект. Плоские глобали
  минифицируются в однобуквенные имена не хуже локальных переменных, а обращение к ним короче,
  чем `state.foo.bar`.

## Стиль

- Без точек с запятой (ASI), как в исходном проекте — просто для единообразия, автоматически
  не проверяется.
- Функции, которые вызываются из других файлов ("публичный" API модуля) — `PascalCase`
  (`CreateCamera`, `SetCameraConstraints`). Локальные хелперы и переменные — `camelCase`.
  Так сразу видно, что можно звать снаружи файла, а что — внутренняя деталь.
- Комментарии — только там, где неочевидна причина (константа-магия, обход особенности
  браузера). Не описывать очевидное.
- Весь **игровой/UI-текст** (заголовки, кнопки, реплики диалога, названия планет) — на
  английском, независимо от того, что комментарии в коде и доки — на русском. js13k —
  англоязычный конкурс, тексты в самой игре ориентированы на игрока, а не на читающего код.
- "Игровое состояние как плоский массив/словарь" — не только entities/objects, но и
  ресурсы игрока: вместо поля на объекте на каждый ресурс — один плоский массив `res`,
  индексируемый именованными константами (`RES_MONEY` и т.п., см. `resources.js`). Новый
  ресурс — это одна новая константа и один элемент массива, не новое поле по всему кодовому
  графу.

## Объекты сцены

Не полноценный ECS (реестр компонентов, битовые маски архетипов и т.п.) — это оверинжиниринг
на масштабе этой игры. Вместо этого:

- **Объект** — плоский объект-литерал. Общие поля: `position` (пригодится позже для
  сортировки по глубине) и `render(viewProj)` — объект **рисует себя сам**: метод-замыкание,
  который хранит свои GL-буферы, шейдерную программу и цвет и сам делает `useProgram` /
  `bindBuffer` / `drawElements`. Нет отдельной системы `RenderXxx(list)`, которая обходит
  список и решает, что рисовать, по набору полей — только `for (o of objects) o.render(vp)`.
- Меш каждого объекта — собственный, не шарится между инстансами (`UploadMesh` в `gl.js`
  создаёт новые буферы на каждый вызов). Это позволяет, например, двум сферам иметь разную
  тесселяцию (`latBands`/`lonBands`), а не быть масштабированной копией одного общего меша.
- Один фабричный слой `CreateMeshObject(gl, position, mesh, scale, color)` (`objects.js`) —
  общая часть (буферы, `render`, model-матрица `position + scale`). Разница между "видами"
  объектов — только в том, *какой генератор меша* ему передали
  (`GenSphereMesh`/`GenCubeMesh` в `geometry.js`), не в отдельных типах/классах объектов.
  `CreateSphereObject`/`CreateCubeObject` — тонкие обёртки над `CreateMeshObject` с разной
  геометрией. Если позже понадобится реально другое *поведение* (не просто другая форма) —
  заводить отдельный вид объекта тогда, не раньше.
- **Пикинг** — `PickObject(camera, ndcX, ndcY, objects)` в `objects.js`: перебирает объекты
  с `onClick` и `radius` (сферический bounding-объём), возвращает ближайший по лучу. Не метод
  объекта — вызывающий код (сцена) сам решает, что делать с результатом.

Список объектов сцены (`ctx.objects`) не глобальный массив, а живёт в контексте (см. ниже) —
им управляют состояния (см. следующий раздел).

## Стейт-машина

Один файл — одно состояние, имя файла — всегда `xxx_state.js`. Состояние — фабричная функция
`CreateXxxState(...)`, возвращающая объект с тремя методами:

```js
function CreateSystemState() {
	let mine = []
	return {
		OnEnter(ctx) { /* построить свои объекты в ctx.objects, настроить камеру/UI */ },
		OnExit(ctx)  { /* убрать за собой то, что сам добавил */ },
		OnUpdate(ctx, dt) { /* применить input к камере, обработать клики, camera.update(dt) */ }
	}
}
```

`ctx` — контекст, общий для всех состояний (создаётся один раз в `main.js`):

```js
const ctx = { gl, objects: [], camera: CreateCamera(), input: CreateInput(canvas) }
```

- `ctx.objects` — граф сцены. **Не сбрасывается автоматически** между состояниями — это
  решение каждого состояния: обычно состояние запоминает у себя (в замыкании, как `mine`
  выше) список объектов, которые само же добавило в `ctx.objects`, и убирает ровно их в
  `OnExit` (см. `RemoveObjects` в `objects.js`). Так один и тот же объект в принципе может
  пережить смену состояния, если два состояния сознательно решат его не трогать — этим
  пользуются `galaxy.js`/`system.js`: звёзды галактики и звезда+планеты системы создаются один
  раз и кешируются, состояния только добавляют/убирают уже существующие инстансы в/из
  `ctx.objects`, а не создают их заново на каждый вход (см. ниже).
- `ctx.camera` — общая орбитальная камера на все сцены, см. [camera.md](camera.md). Она же
  общий источник тонкой, но важной детали: `camera.theta` не входит ни в какие constraints и
  никогда не сбрасывается автоматически — состояние с фиксированным ракурсом (диалог/бой/обзор)
  обязано выставить `theta` само в `OnEnter`, иначе кадр отнаследует случайный угол от предыдущей
  сцены. Подробности и известный баг на эту тему — [camera.md](camera.md#theta-и-фиксированный-ракурс).
- `ctx.input` — сырые данные пойнтера за кадр (см. `input.js`), состояние само решает, что
  с ними делать в `OnUpdate` — камера не подписана на input напрямую. Состояния с
  фиксированным ракурсом (диалог/бой) просто не читают `ctx.input` вообще — так же, как раньше
  делало меню.

Переключение состояния — это подстановка нового экземпляра состояния вместо текущего.
Технически это делает `SetState(next)` в `main.js`:

```js
function SetState(next) {
	if (currentState && currentState.OnExit) currentState.OnExit(ctx)
	ClearUI()
	currentState = next
	if (currentState.OnEnter) currentState.OnEnter(ctx)
}
```

`OnExit` предыдущего состояния и `OnEnter` следующего вызываются автоматически как часть
этой подстановки — сами состояния (и обработчики кликов внутри них) просто зовут
`SetState(CreateXxxState(...))`, ни о чём другом не заботясь. UI (`ClearUI()`) по-прежнему
чистится централизованно на каждом переключении — это не "граф сцены", см.
[ui.md](ui.md).

Игровой цикл (`requestAnimationFrame`) на каждом кадре: сначала дешёвая проверка
`canvas.width !== canvas.clientWidth` (см. "Ресайз" ниже), затем `currentState.OnUpdate(ctx, dt)`,
затем очистка канваса и `for (o of ctx.objects) o.render(viewProj)`, затем `ctx.input.update()`
(сбрасывает разовые поля инпута — клик/дельты — на следующий кадр).

### Состояния

| файл                       | состояние            | камера | что в сцене |
|-----------------------------|----------------------|--------|-------------|
| `menu_state.js`             | меню                 | фикс. ракурс, автоповорот | заголовок, декоративное солнце, кнопка Play → генерирует галактику (один раз) → `galaxy_state.js` |
| `galaxy_state.js`           | карта галактики       | верхняя полусфера, drag/zoom | 25 звёзд (кеш, `galaxy.js`), красный маркер = текущая звезда, клик по звезде в радиусе → зелёный маркер + кнопка прыжка → `hyperjump_state.js` |
| `hyperjump_state.js`        | переход (межзвёздный) | заморожена | вращающийся радужный тоннель из кубиков; по таймеру → `system_state.js` для новой звезды |
| `system_state.js`           | карта системы          | верхняя полусфера, drag/zoom | звезда + 2-4 планеты (кеш на индекс звезды, `system.js`), кораблик крутится вокруг звезды, клик по звезде → `galaxy_state.js`, клик по планете в радиусе → зелёный маркер + кнопка прыжка → `system_travel_state.js` |
| `system_travel_state.js`    | переход (локальный)   | заморожена | звёзды летят в камеру; по таймеру → `NextPlanetState(planet, 'jump')` |
| `dialog_state.js`           | событие: диалог       | фикс. ракурс | кубик-собеседник + текст + до 4 кнопок выбора, одноходовый → `NextPlanetState(planet, 'dialog')` |
| `battle_state.js`           | событие: бой          | фикс. ракурс | два кубика + кубик-пулька + кнопка Next (−1 жизнь) → `NextPlanetState(planet, 'battle')` |
| `overview_state.js`         | событие: обзор        | полная сфера, drag/zoom | планета + кораблик, кнопки Search (собрать ресурсы планеты) и Next → `system_state.js` |

Полное описание игрового цикла и баланса ресурсов — [concept.md](concept.md), не здесь;
architecture.md фиксирует только форму (состояния/файлы/контракты), а не цифры/геймдизайн.

### Кеширование galaxy/system и оркестрация планетных событий

`galaxy.js` и `system.js` — не состояния, а модули данных, на которые состояния опираются:

- `galaxy.js`: `GenerateGalaxy(ctx)` вызывается ровно один раз (из `menu_state.js`), создаёт
  25 звёзд-объектов и оба маркера и больше не трогает GL — `galaxy_state.js` только
  добавляет/убирает уже готовые инстансы в/из `ctx.objects`.
- `system.js`: `GetSystem(ctx, starIndex)` — ленивый кеш по индексу звезды (`systemCache`).
  Первый визит генерирует звезду+планеты (случайно, `Math.random()` — псевдослучайности с
  сидом по индексу не нужно, раз результат и так кешируется навсегда), последующие визиты
  отдают тот же самый инстанс — поэтому `planet.dialogDone`/`battleDone` и собранные ресурсы
  переживают уход со сцены и возврат на неё.
- `system.js`'s `NextPlanetState(planet, from)` — единственное место, решающее, какое
  под-состояние события открыть дальше (диалог → бой → обзор, пропуская отсутствующее/уже
  потраченное). И вход в цепочку (`system_travel_state.js`, `from: 'jump'`), и каждый шаг
  внутри неё (`dialog_state.js`/`battle_state.js`, `from: 'dialog'`/`'battle'`) зовут именно
  эту функцию вместо того, чтобы каждое само знало про соседние состояния — иначе три файла
  события были бы зашиты друг на друга напрямую.

## Ресайз

Раньше ресайз слушался через `resize`-событие на `window`, и он ненадёжен (не гарантированно
стреляет при любом изменении фактического размера канваса — сворачивание/разворачивание
DevTools и некоторые способы встраивания страницы событие не шлют). Вместо этого `main.js`
каждый кадр дёшево сравнивает `canvas.width`/`canvas.height` (буфер отрисовки) с
`canvas.clientWidth`/`clientHeight` (реальный CSS-размер) и вызывает `Resize()`, если они
разошлись — это не привязано к событию вообще и ловит любую причину рассинхронизации, а не
только `resize` на `window`.
