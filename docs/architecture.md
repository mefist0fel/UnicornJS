# Архитектура и конвенции

Организация кода унаследована от предыдущего js13k-проекта (`../js13k_city`, Castle Wars JS) —
она хорошо показала себя под жёсткий бюджет размера и решётку google-closure-compiler /
внешних минификаторов. Здесь тот же подход, адаптированный под настоящий WebGL вместо
canvas2d-псевдо-3D.

## Никаких модулей, никаких классов

- Файлы — обычные `<script>`, без ES-модулей (`import`/`export` жрут байты в non-advanced
  минификации и требуют `type="module"` + CORS-нюансов при `file://`). Порядок подключения
  задаётся один раз в `html/index.html` и **является manifest'ом сборки** — `build.py` читает
  этот же порядок, чтобы не дублировать список файлов (см. [build.md](build.md)).
- Никаких `class`. Объекты создаются фабричными функциями `CreateXxx(...)`, возвращающими
  плоский объект-литерал с методами-замыканиями. Это дешевле для минификатора (нет цепочки
  прототипов, поля манглятся как обычные свойства объекта) и не требует `this`/`bind`.

  ```js
  function CreateSphereEntity(position, radius, color) {
    return {
      position, radius, color,
      onClick: null,
    }
  }
  ```

- Общее изменяемое состояние — плоские глобальные переменные (`var`/`let` на верхнем уровне
  файла), а не одна большая конфигурация/синглтон-объект. Плоские глобали минифицируются в
  однобуквенные имена не хуже локальных переменных, а обращение к ним короче, чем
  `state.foo.bar`.

## Стиль

- Без точек с запятой (ASI), как в исходном проекте — просто для единообразия, автоматически
  не проверяется.
- Функции, которые вызываются из других файлов ("публичный" API модуля) — `PascalCase`
  (`CreateCamera`, `SetCameraConstraints`). Локальные хелперы и переменные — `camelCase`.
  Так сразу видно, что можно звать снаружи файла, а что — внутренняя деталь.
- Комментарии — только там, где неочевидна причина (константа-магия, обход особенности
  браузера). Не описывать очевидное.

## ECS-лайт

Полноценный ECS (с реестром компонентов, битовыми масками архетипов и т.п.) на масштабе этой
игры — оверинжиниринг и лишние байты. Вместо этого:

- **Entity** — обычный плоский объект в массиве `entities`.
- **Component** — просто поле на этом объекте. Наличие поля = наличие компонента.
  Например: `position` + `radius` → у сущности есть форма-сфера; `color` → есть материал;
  `onClick` → сущность кликабельна.
- **System** — обычная функция, которая проходит по `entities` и обрабатывает только те,
  у кого есть нужные поля (проверка `if (e.radius)` и т.п., без формального query-языка).

Пример систем (`html/js/entities.js`):

- `RenderEntities(entities, camera)` — рисует все сущности с `position`+`radius`+`color`.
- `PickEntity(entities, ray)` — пересечение луча со всеми сущностями, у которых есть `radius`,
  возвращает ближайшую; вызывающий код сам решает, что делать (обычно — дёрнуть `onClick`).

Это прямое расширение паттерна `objects3d` из js13k_city (там каждый объект в общем массиве
имел `prepareScene()`/`draw()`), просто с явным разделением "что нарисовать" и "что кликнули"
на отдельные проходы, и с полями-компонентами вместо методов.

## Стейт-машина

Как и в js13k_city: одна глобальная переменная-указатель на функцию текущего состояния
(`updateFn`) плюс `setState(id)`, которая:

1. очищает `entities` (и любые прочие сцен-локальные списки);
2. населяет `entities` заново под новое состояние;
3. настраивает ограничители орбитальной камеры под сцену (см. [camera.md](camera.md));
4. монтирует нужную UI-панель (см. [ui.md](ui.md));
5. переключает `updateFn` на функцию апдейта нового состояния.

Три состояния:

| id | состояние     | камера                          | что в сцене |
|----|---------------|----------------------------------|-------------|
| `MENU`   | меню            | солнечная система на фоне, автоповорот | заголовок + кнопка "Играть" |
| `SOLAR`  | солнечная система | верхняя полусфера, drag/zoom      | солнце + сферы-планеты, клик по планете → `PLANET` |
| `PLANET` | планета         | полная сфера, drag/zoom           | одна большая сфера-планета, кнопка "Назад" → `SOLAR` |

Переход между состояниями запускается двумя путями — оба сходятся в `setState`:

- **UI-кнопкой** (DOM `click`) — например "Играть" в меню, "Назад" на планете;
- **ECS-пикингом** — клик по сфере-планете в 3D-сцене солнечной системы (`onClick` сущности
  вызывает `setState(PLANET, planetData)`).

Игровой цикл (`requestAnimationFrame`) на каждом кадре: обновить камеру по input, вызвать
`updateFn(dt)`, отрендерить `entities` через `RenderEntities`.

## Файлы (`html/js/`, порядок = порядок подключения)

| файл          | отвечает за |
|---------------|-------------|
| `gl.js`       | инициализация WebGL-контекста, компиляция шейдеров, mat4/vec3 математика, генерация меша сферы |
| `input.js`    | pointer-события: drag → вращение камеры, wheel → зум, различение клика и драга |
| `camera.js`   | орбитальная камера: сферические координаты, ограничители, view/projection, луч для пикинга |
| `entities.js` | ECS-лайт: массив `entities`, системы рендера и пикинга |
| `ui.js`       | DOM-панели и кнопки поверх канваса (см. [ui.md](ui.md)) |
| `scenes.js`   | наполнение `entities`/камеры для каждого состояния (меню/система/планета) |
| `main.js`     | стейт-машина, `setState`, игровой цикл, точка входа |

Добавляя новый файл — не забыть вписать его `<script src>` в `html/index.html` в правильном
месте (используется как есть в `build.py`, отдельного манифеста нет).
