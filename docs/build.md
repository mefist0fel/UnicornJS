# Сборка и бюджет размера

Бюджет: **zip-архив релиза ≤ 13 312 байт** (правило js13k). Сборка автоматизирована одним
Python-скриптом; минификация делается локально установленным `google-closure-compiler`
(npm-пакет), без ручного похода на внешний сайт.

## Почему Python-скрипт, а не node.js-таск-раннер

Оркестрация пайплайна (конкатенация → минификация → сборка HTML → zip → копирование) —
по-прежнему `python html/packed/build.py`, не npm-скрипт. Не по идеологическим причинам: сам
`google-closure-compiler` — npm-пакет и требует node.js, он уже используется как внешний
инструмент, который просто дёргается через `subprocess`. Но заводить ради этого
`package.json`/`node_modules`/лок-файлы под сам оркестратор — не нужно, когда 80-строчный
Python-скрипт (stdlib, уже есть в системе) делает то же самое без лишней инфраструктуры.
Если для какого-то будущего шага понадобится npm-пакет, которого нет в системе — это сигнал
остановиться и оценить, оправдан ли он, а не сигнал переезжать на node целиком.

## Требования

- Python 3 (stdlib, ничего доустанавливать не нужно).
- `google-closure-compiler`, установлен глобально: `npm install -g google-closure-compiler`
  (уже стоит в системе разработки; `build.py` ищет его на `PATH` и падает с понятной ошибкой,
  если не находит).

## Этапы

1. **Разработка** — просто открыть `html/index.html`. Файлы `html/js/*.js` подключены
   отдельными `<script src>` в порядке зависимостей (см. [architecture.md](architecture.md)),
   сборка не нужна.

2. **Полный цикл** — `python html/packed/build.py`:
   - парсит `html/index.html`, вытаскивает список `<script src="js/....js">` **в том порядке,
     в котором они там перечислены** — это единственный manifest, второй раз файлы нигде не
     перечисляются;
   - склеивает содержимое этих файлов в `html/packed/bundle.js`;
   - минифицирует его локальным `google-closure-compiler -O ADVANCED` (через `subprocess`) в
     `html/packed/bundle.min.js` — падает с полным выводом компилятора, если тот вернул
     ошибку; предупреждения печатаются, но не останавливают сборку;
   - собирает финальный `html/packed/index.html` — тот же HTML-шаблон, но вместо набора
     `<script src>` один инлайновый `<script>` с минифицированным кодом;
   - зипует его (`zipfile`, `ZIP_DEFLATED`, максимальное сжатие) **в двух местах**:
     `html/packed/game.zip` (рядом со скриптом сборки) и `dist/game.zip` (результирующая папка
     релиза) — это одна и та же сборка, просто с копией под рукой там же, где сам пайплайн;
   - печатает размер зипа и остаток бюджета (`13312 - size`). Если бюджет превышен —
     скрипт завершается с ненулевым кодом.

3. **Быстрая проверка без минификации** — `python html/packed/build.py --skip-minify`:
   тот же конкатенированный `bundle.js`, инлайненный в `html/packed/index.html` как есть, без
   вызова компилятора и без zip (неминифицированный размер не отражает реальный бюджет, поэтому
   упаковывать его в архив нет смысла). Полезно, когда просто нужно быстро проверить, что
   конкатенация ничего не сломала, до похода к компилятору — тот же смысл, что раньше был у
   промежуточного шага без `--pack`, просто теперь это явный флаг, а не отдельная стадия.

## Инварианты

- `html/packed/bundle.js`, `html/packed/bundle.min.js`, `html/packed/index.html` и
  `html/packed/game.zip` — сгенерированные/промежуточные файлы, в git не коммитятся (см.
  `.gitignore`). `dist/` — тоже.
- HTML-шаблон (стили, `<canvas>`, `#ui`) не дублируется между dev и packed версией — и
  `build.py`, и ручная разработка используют один и тот же `html/index.html` как источник
  разметки; packed-версия отличается только тем, что блок `<script src>` заменён на один
  инлайновый `<script>`.
- Минификатор вызывается на уже склеенном `bundle.js` одним файлом, а не на списке исходников
  по отдельности — так `build.py` остаётся единственным местом, где перечислены файлы сборки
  (см. [architecture.md](architecture.md)); заводить второй список файлов специально под
  компилятор означало бы держать два манифеста в синхроне вручную.
- Если размер зип-архива начинает подбираться к лимиту — сначала смотреть на ассеты
  (шрифты/текстуры/аудио — их пока нет вообще, см. [concept.md](concept.md)), потом на JS.
  Убирать читаемость кода (короткие имена, отказ от абстракций) — то, ради чего вообще выбран
  этот стиль организации кода, см. [architecture.md](architecture.md).
